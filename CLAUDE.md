## Что это за проект

**Минги-Тау** — закрытое мобильное/веб-приложение (сообщество) для карачаевцев
и балкарцев по всему миру. Вход только по приглашению. Подпись бренда:
«Карачаево-Балкарское сообщество». Проект некоммерческий.

Основатель проекта — **Мурат Курджиев**, не программист. Правила работы с ним:

- Строго пошагово, одно действие за раз, без жаргона.

- Отправка на GitHub: Source Control → Commit → Sync Changes.

  (`-c` обязателен — чистит кэш).
- В `.gitignore` добавлена строка `.env` (раньше был только `.env*.local`
  — простой `.env` УТЁК БЫ в публичный репозиторий).

## ПОДТВЕРЖДЕНИЕ ПОЧТЫ (Веха 8, работает на ВМ с Вех 28–29)

Почта подтверждается **своим** 6-значным кодом (не механизмом Supabase) —
полностью на ВМ Яндекса.

- Ящик проекта: `mingi-tau-id@yandex.ru`, SMTP `smtp.yandex.ru:465`,
  пароль приложения «Почта», в ящике включён IMAP/SMTP.
- Код функции в репозитории: `supabase/functions/send-email-code/index.ts`
  (первая строка `// @ts-nocheck` — файл для Deno, красные подчёркивания
  VS Code — норма).
- На ВМ функция лежит в `~/supabase/volumes/functions/send-email-code/`.
  Секреты — строки `YANDEX_SMTP_USER` / `YANDEX_SMTP_PASS` в
  `~/supabase/.env`, проброшены в контейнер в `docker-compose.yml`
  (раздел `environment:` службы functions, после `JWT_SECRET`).
  После смены секретов: `cd ~/supabase && docker compose up -d functions`.
- ⚠️ В `~/supabase/.env` ОБЯЗАТЕЛЬНО `ENABLE_EMAIL_AUTOCONFIRM=true`:
  подтверждение у нас своё, а при `false` служба auth после регистрации
  сама шлёт письмо через несуществующий тестовый ящик `supabase-mail`
  и ВСЯ регистрация падает с пустой ошибкой `{}` (поймано и починено
  в Вехе 29). Там же `SITE_URL` и `API_EXTERNAL_URL` =
  `https://api.mingi-tau.ru`.
- Таблица `public.email_verification_codes`, RLS включён.
- Edge Function `send-email-code` (send / verify): код 10 минут, пауза
  60 сек, 5 попыток, старые коды удаляются.
- **Письмо: тема и имя отправителя ТОЛЬКО ЛАТИНИЦЕЙ** (кириллица в
  заголовке — крякозябры; ручное кодирование RFC 2047 — двойное

- Поток регистрации: контакты → код → анкета. Инвайт тратится при

  переписка внутри, кнопки «Изучить» нет — старый экран деталей про них
  не знает). В карточке: автор (нажатие → профиль), переписка, поле
  ответа, «Взять в работу» / «Закрыть». «Закрыть» срабатывает СРАЗУ, без
  модального окна; пояснения модератор пишет через «Ответить».
- «Одна переписка — одна карточка»: новое сообщение человека добавляется
  в его ОТКРЫТОЕ обращение (даже если оно в работе); новая карточка
  создаётся только после закрытия старой.
- **Обращения удалённых видит ТОЛЬКО основатель** (решает о
  восстановлении): фильтр в сервисе (`author.is_deleted`), в счётчике и в
  уведомлениях. У удалённого автора вместо поля ответа — пояснение и
  только «Закрыть».
- Сервис (`moderationService`): getOpenAppeals, getClosedAppeals,
  takeAppeal, closeAppeal, replyToAppeal, getAppealMessages,
  sendAppealMessage (для участника), restoreUser; обращения входят в
  счётчик задач модерации.
- Триггеры в базе: `trg_appeal_message` → `notify_on_appeal_message`
  (участник написал → модераторам, `is_moderation_task=true`, ссылка в
  new/in_progress; удалённый написал → только основателю, заголовок
  «Обращение удалённого участника»; модератор ответил → автору);
  `trg_appeal_closed` → `notify_on_appeal_closed` (закрытие → автору,
  с review_note). Старый `notify_moderators_on_user_message` пропускает
  `request_type='appeal'` (иначе был дубль уведомлений).

## RLS НА ПЕРЕПИСКАХ МОДЕРАЦИИ (Веха 43) + ЧЕК-ЛИСТ ПРОВЕРКИ

`moderation_messages` хранит три типа переписок (request_type →
request_id): `invite_request` → id участника (регистрация) ИЛИ id
строки invite_requests (просьба инвайта от анонима, экран
«Запросить инвайт»); `appeal` → id обращения; `name_change_request`
→ id запроса смены имени. Правила (по образцу appeals):

- mm_select: модераторы — всё; участник — свои переписки всех трёх
  типов, КРОМЕ строк `is_internal=true` (внутренние заметки).
- mm_insert: модераторы — всё; участник — свои сообщения
  (author_user_id = он) в свою заявку и своё обращение; аноним —
  ТОЛЬКО системный след (`author_role='system'`, author_user_id null,
  request_type='invite_request') — без этой ветки ломается приём
  просьб об инвайте.
- UPDATE/DELETE: политик нет = запрещены всем (код их не использует).
- Триггеры уведомлений — SECURITY DEFINER, RLS их не задевает.
  Рубильник «Выходной» работает: глушилка стоит на notifications.

**ЧЕК-ЛИСТ живой проверки переписок/модерации** (гонять после любых
правок RLS, триггеров уведомлений или экранов переписок):

1. Аноним (инкогнито) отправляет «Запросить инвайт» — проходит.
2. Модератору само приходит уведомление «Запрос инвайта», нажатие —
   прицел на карточку (подсветка + прокрутка).
3. На карточке ярлык «Запрос инвайта», в фильтрах «Нового» — «Инвайты».
4. Модерация: диалоги в карточках читаются.
5. Участник пишет в открытое обращение — уходит, карточка модератора
   оживает сама.
6. Ответ модератора сам появляется у участника в contact-admin.
7. Закрытие обращения — у участника экран сам возвращается к форме.
8. Экран ожидания (pending): переписка заявки видна, дописка уходит.
9. contact-admin открывается без скачка: крутилка → сразу нужный вид.

  attachment_path — в пузырьке остаётся заглушка «Фото недоступно /
  файл недоступен», сама переписка не трогается. Проверен боевым
  запуском (0 к чистке — так и должно).
- **Разрешения и приватность (ответы владельцу):** ничего не
  запрашивается автоматически — на вебе выбор фото это обычное окно
  файла; в телефон ничего само не сохраняется, файлы живут только на

— каждый элемент это ОБЪЕКТ с именем таблицы и необязательным фильтром
по одной строке (не голая строка!).

**Самолечение (Веха 41):** при статусах CHANNEL_ERROR / TIMED_OUT /
CLOSED служба сама пересоздаёт канал с паузой (3 с, при повторных
сбоях удваивается до потолка 30 с, после успеха сбрасывается); после
восстановления вызывает `onChange` — экран перечитывает данные и
догоняет пропущенное за время обрыва. Уникальные имена каналов служба
делает сама (сквозной номер) — экранам выдумывать их больше не нужно.
⚠️ Капкан, пойманный живым тестом: выброшенный канал перед смертью
кричит «CLOSED»; служба слушает ТОЛЬКО действующий канал (`channel !==
myChannel` → игнор), иначе — бесконечный хоровод замен. Проверка
самолечения: `cd ~/supabase && docker compose restart realtime` на ВМ
и смотреть доклады «Живой эфир: …» в консоли браузера. Обкатано в бою

## ПРАВИЛА ДОСТУПА И БЛОКИРОВОК (Веха 17, дополнено Вехой 35)

**Две разные блокировки:**

1. **Личная** (участник ↔ участник, `userBlockService`): скрывают
   контакты друг друга, писать нельзя. Заблокировавший (А) видит на
   карточке Б серую строчку «Участник заблокирован» — напоминание себе.
   Б и остальные НЕ видят ничего; единственный намёк для Б — в чате
   пропадает поле ввода, БЕЗ пояснений (решение владельца).
2. **Административная** (`is_blocked`, кнопка у админов): человек
   отключён от сообщества — часовой уводит его на `access-restricted`
   (оттуда — обращение к администрации и автовозврат после снятия).
   Правило в базе прячет его из списков и карточек для обычных
   участников. Красный чип «ЗАБЛОКИРОВАН» под аватаром видят ТОЛЬКО
   основатель и модераторы. В меню «⋮» пункт-переключатель:
   «Заблокировать участника» / «Снять блокировку участника»
   (список заблокированных со снятием есть и в Модерации).
   Обращения от заблокированных в модерации: пометка и только
   «Закрыть», без поля ответа (решение владельца, Веха 35).

- Модератор видит скрытые контакты, только пока его не заблокировали.
- **Основателю доступно всё и всегда** — блокировки на него не действуют.
- Удаление/восстановление — только основатель (см. раздел выше). Вход
  удалённого/заблокированного перехватывают `app/index.tsx` и
  `login.tsx`; на живую это делает часовой `AccountGuard` (Веха 35).
